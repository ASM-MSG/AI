# MSG-367 인코딩 통합 전후 실측

2026-08-11, AI 전용 t3.small(MSG-339 분리 인스턴스)에서 측정했다.

**결론: 완료 조건 4개 전부 통과. 유휴 API 왕복[^1] 중앙값이 221초에서 192초로 13.1% 짧아졌고,
재생본에서 mp4v 흔적이 사라졌으며, 결과물 크기가 21.9% 줄었다.** 티켓이 "화질이 이유고 속도
기대치는 낮게"라고 못 박은 작업인데, 속도도 기대(약 9%)보다 더 나왔다.

원자료:

- 전후 요약: `results/MSG-367-bench.json`
- 탐지·블러 동일성 대조(macOS 기능 판정): `results/MSG-367-identity.json`

## 판정 (티켓 완료 조건)

| 완료 조건 | 근거 | 판정 |
|---|---|---|
| AI 레포 안 전체 프레임 인코딩 1회 | `downscale()` 무필터 바이패스 + rawvideo 파이프 단일 인코딩. `server.py --smoke`의 바이패스 어서션(반환==src, dst 미생성), `raw.mp4` 경로 코드에서 소멸 | 통과 |
| 재생본에 mp4v 경유 흔적 없음 | 전후 6건 결과물 ffprobe 전부 `h264`. 배포 E2E(H.264 검사 포함) 초록불 2회(머지 CD + 복구 CD) | 통과 |
| 블러 품질·탐지 결과 동일 | 실영상 3종(crowd·plates·kr-plates) 전후 detections·프레임 수 완전 동일(`MSG-367-identity.json`). EC2 결과물도 길이 29.029초 동일, 버전별 크기 결정적(3회 모두 바이트 단위 일치) | 통과 |
| 건당 처리 시간이 나빠지지 않음 | 아래 전후 비교 — 중앙값 13.1% 단축 | 통과 |

## 전후 비교

같은 29초 `crowd` 1080p 무음 샘플을 유휴 상태에서 `POST /jobs` 제출부터 `DONE`까지 3회씩
재었다(`scripts/ec2-ai-load-test.sh` N=1). 변경 전은 머지 직전 main(`c5f36a6`)을 임시 브랜치로
배포해 같은 조건을 만들었다. MSG-142 비중표는 `bench.run` 내부만 계측해 ffmpeg 패스 2·4가
빠져 있으므로(스펙 검증 계획 4), stage 비중이 아니라 API 왕복으로 비교한다.

| 버전 | 실행 시간 | 중앙값 | 결과물 크기 | 호스트 피크 메모리 |
|---|---|---:|---:|---:|
| 변경 전 (`c5f36a6`) | 221, 221, 218초 | **221초** | 8,985,532B | 1,197MB |
| 변경 후 (main) | 199, 192, 184초 | **192초** | 7,016,204B | 1,191MB |

- **처리 시간 -13.1%** (중앙값 -29초). 티켓 추정(인코딩 비중 10~15%)과 부합한다 — 없앤 것이
  풀프레임 재인코딩 2회(패스 2·4)와 mp4v 기록 1회이므로.
- **결과물 -21.9%**. 같은 최종 코덱(h264)인데 작아진 것은 mp4v 4세대 경유가 만들던 압축
  노이즈가 사라져 인코더가 노이즈에 비트를 쓰지 않게 된 것으로 해석된다 — "화질" 목표가
  파일 크기로 드러난 방증이다.
- **메모리·안정성**: 호스트 피크가 변경 전과 같은 수준(1,191 vs 1,197MB)이고 OOM·컨테이너
  재시작 0 — 추론과 동시에 도는 ffmpeg 인코더가 추가 스왑을 부르지 않는다(성공 기준 4행의
  확인 항목). 변경 후 첫 실행에서 스왑 I/O 연속 3회[^2]가 한 번 찍혔는데 배포 직후 첫 잡의
  모델 로드 워밍업이다 — 스왑 사용량 증가 없음, 이후 실행은 연속 1회로 복귀.

## 한계

- 측정 샘플이 무음이라 오디오 경로(`-af apad` 포함)는 이 수치에 없다. 오디오 경로의 기능
  검증은 smoke(사인톤 왕복·절단 회귀 어서션)와 로컬 kr-plates 대조(aac, 900프레임 보존)로
  했다. 오디오 있는 입력은 aac 인코딩이 더해지므로 절대 초는 약간 늘 수 있으나, 그 비용은
  변경 전에도 패스 2에서 치르던 것이라 전후 방향은 뒤집히지 않는다.
- 호스트 피크 메모리는 `free -m` 기준이라 MSG-339의 파이썬 프로세스 피크(503.7MB)와 계측
  단위가 다르다 — 세대 간 비교는 이 리포트의 전후 값끼리만 유효하다.

[^1]: 유휴 API 왕복: 다른 잡이 없는 상태에서 `POST /jobs` 제출부터 상태가 `DONE`이 될 때까지의 시간. 큐 대기와 서버 오버헤드를 포함한 사용자 관점 처리 시간이라, 내부 stage 합계보다 비교 기준으로 정직하다.
[^2]: 스왑 I/O 연속 기준: 10초 간격 표본에서 swap-in/out이 연속으로 몇 번 찍혔는지다. MSG-339부터 "연속 3회 이상 = 메모리 압박" 신호로 쓴다 — 순간 스파이크와 지속 스래싱을 구분하는 장치다.
