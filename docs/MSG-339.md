# MSG-339: AI 블러 서버를 분리해 여러 영상을 더 빠르게 처리한다

> 요구사항 정본: `docs/prd/MSG-339-prd.md` (상태: 검토됨)
> 이 문서는 PRD의 기능 요구사항과 비기능 요구사항에 구현 방법만 붙인다. 내용이 어긋나면 PRD가 이긴다.

## 개요

AI 컨테이너를 백엔드, PostgreSQL, Redis, Kafka가 실행 중인 기존 EC2에서 전용 t3.small로 옮긴다.
FastAPI는 한 uvicorn 프로세스로 유지한다. 같은 인메모리 큐를 읽는 워커 스레드[^1]를 최대 2개
띄우고, 한 작업 안에서는 프레임 2장 또는 4장을 묶어 배치 추론[^2]한다.

초기값과 롤백값은 워커 1개, 배치 1개다. 배치 2와 4, 워커 2개는 전용 EC2 실측을 통과한 조합만
채택한다. 외부 큐, 다중 uvicorn 프로세스, 모델 상주 캐시는 추가하지 않는다.

## 배경과 목표

MSG-151에서 기존 dev t3.small에 영상 6건을 동시에 요청했을 때 메모리 1,480MB, 스왑 606MB,
load1 7.13을 기록했다. 전 건 완료됐지만 AI 단일 워커가 건당 약 2.6분씩 순차 처리해 시간당
처리량은 약 20건에서 23건에 머물렀다(`results/MSG-151-report.md`).

OpenVINO는 약 5%만 빨랐고 프레임 스킵은 도로 영상 번호판 커버리지가 46.1%까지 떨어졌다
(`results/MSG-207-report.md`). `imgsz` 하향도 번호판 recall이 320에서 0.038로 떨어져 기각됐다
(`results/MSG-281-report.md`). 정확도를 유지하면서 남은 소프트웨어 조정축은 배치 추론이다.

목표는 전용 t3.small의 워커 1개, 배치 1개보다 단일 처리 시간을 20% 이상 줄이고 시간당 처리량을
1.7배 이상 높이는 데 있다. 동시 처리 중 작업 하나의 실제 처리 시간 증가는 30% 이하로 제한하며,
동시 6건에서 작업 유실, OOM[^3], 컨테이너 재시작을 허용하지 않는다.

## 성공 기준

| 항목 | 판정 기준 |
|---|---|
| 단일 처리 시간 | 워커 1, 배치 2 또는 4의 `crowd` 29초 영상 처리 시간이 워커 1, 배치 1보다 20% 이상 짧다 |
| 처리량 | 워커 2와 채택 배치의 동시 6건 처리량이 워커 1, 배치 1보다 1.7배 이상 높다 |
| 동시 처리 영향 | 후보 설정의 동시 6건 중 가장 긴 `PROCESSING` 관측 시간이 같은 설정의 단일 작업보다 30% 넘게 길지 않다 |
| 검출 동등성 | 배치 1 상자를 기준으로 얼굴과 번호판의 IoU[^4] 0.5 이상 상대 recall이 각각 1.000이다 |
| 프레임 보존 | 입력과 출력의 프레임 수와 순서가 같고 마지막 불완전 배치도 출력된다 |
| 안정성 | 동시 6건이 모두 `DONE`이고 결과 영상이 재생된다. OOM, 컨테이너 재시작, 작업 유실은 0건이다 |
| 스왑 | 10초 간격 표본에서 swap-in 또는 swap-out이 3회 연속 발생하지 않는다 |
| 계약 | 기존 HTTP 경로, 요청, 응답 필드, 상태 전이가 바뀌지 않는다 |
| 비용 | 시간당 0.026달러의 t3.small을 기준으로 EBS, EIP, CPU 크레딧[^5] 비용을 기록한다 |

같은 전용 EC2와 영상에서 후보별 3회 실행 중앙값을 비교한다. 최초 모델 다운로드는 제외하지만
`bench.run()` 안의 모델 로드는 포함한다. 기존 웜 실측에서 모델 로드는 2.277초에서 2.337초로
전체의 1.2%에서 1.3%였고 피크 메모리는 886MB에서 906MB였다
(`results/ec2-aarch64-2core-{normal,crowd,plates}.json`). 모델 상주만으로 20% 목표를 만들 수 없고
워커별 메모리만 계속 점유하므로 현재의 작업별 로드를 유지한다.

## 구현 범위

### 실행 구조

- `AI_WORKERS`는 `1` 또는 `2`, `AI_BATCH_SIZE`는 `1`, `2`, `4`만 허용한다. 기본값은 모두 `1`이며
  다른 값은 시작 오류로 처리한다.
- `server.py`의 전역 `jobs`와 `queue.Queue`를 한 프로세스에서 공유한다. 워커 수만큼 현재
  `worker()`를 데몬 스레드로 시작한다.
- uvicorn `--workers`는 쓰지 않는다. 프로세스가 나뉘면 `jobs`와 큐도 갈라져 조회 404와 작업
  유실이 생길 수 있다.
- 현재 `bench.run()`의 작업별 `load_models()`를 유지한다. 동시에 실행되는 작업은 서로 다른 얼굴 및
  번호판 모델 인스턴스를 쓰며, 워커 사이 모델 공유와 추론 잠금은 금지한다.[^1]
- 운영의 `AI_INFER_STRIDE`는 `1`로 유지한다. 배치 크기와 프레임 스킵을 함께 바꾸지 않는다.
- 새 의존성을 추가하지 않고 `Dockerfile`, `requirements.txt`, `.github/workflows/cd-dev.yml`은
  변경하지 않는다.

### 인프라

| 항목 | 값 |
|---|---|
| EC2 | 서울 리전, 기존 BE와 같은 VPC 및 가용 영역, Ubuntu 24.04, t3.small |
| 저장 공간 | gp3 20GB, 재부팅 후에도 유지되는 2GB 스왑 |
| 보안 그룹 | 8000 포트는 기존 BE 보안 그룹만 소스로 허용. 22 포트는 GitHub 호스팅 러너의 SSH 배포를 위해 공개하되 키 인증만 허용하고 비밀번호 및 root 로그인을 막음 |
| 주소 | EIP는 GitHub Actions SSH 배포에 사용하고 BE는 AI의 VPC 사설 주소로 호출 |

AI 개발 환경과 운영 환경은 나누지 않는다. GitHub Actions의 `DEV_EC2_HOST`만 새 EIP로 바꾸며,
BE의 `AI_BASE_URL`은 새 AI 인스턴스의 사설 IP와 8000 포트로 바꾼다. 8000 포트는 공인 인터넷에 열지 않는다.
22 포트 공개는 현재 SSH 배포를 유지하는 데 따른 제약이다. SSM 또는 GitHub OIDC로 배포 방식을
바꾸기 전까지 보안 그룹만으로 GitHub 호스팅 러너의 변동 주소를 고정할 수 없다.

## 처리 로직

1. `POST /jobs`는 현재처럼 job 상태를 만든 뒤 `queue.Queue`에 넣고 `202`를 반환한다. FIFO[^6]로
   꺼내는 순서는 유지하지만 워커별 처리 시간이 달라 완료 순서는 바뀔 수 있다.
2. 워커는 서로 다른 잡 디렉터리와 임시 디렉터리를 사용한다. 한 작업이 `FAILED`가 되어도 다른 작업의
   상태와 결과는 바꾸지 않는다.
3. 각 작업은 기존 순서인 다운스케일, 프리체크, 블러 및 하이라이트, H.264 인코딩을 유지한다.
4. `bench.run()`은 `VideoCapture`에서 설정한 배치 크기만큼만 프레임을 읽는다. 얼굴 모델과 번호판
   모델에 같은 프레임 목록을 전달하고 결과 목록을 입력 순서대로 블러 처리해 `VideoWriter`에 쓴다.
5. EOF에 남은 1장에서 3장도 같은 경로로 처리한다. 영상 전체 프레임을 메모리에 보관하지 않는다.

Ultralytics는 이미지 목록 입력과 입력 순서에 대응하는 결과 목록을 지원한다.[^2] 한 영상 안에서는
프레임 해상도가 같으므로 배치 padding 조건도 같다. 기존 단계별 시간 이름과 리포트 필드는 유지한다.

배포 스크립트는 AI 인스턴스의 `$HOME/fillmap-ai.env`에서 `AI_WORKERS`와 `AI_BATCH_SIZE`를 읽는다.
파일이 없으면 `1`, `1`로 실행한다. 장애나 자원 압박이 생기면 두 값을 `1`로 되돌리고 같은 스크립트를
재실행한다. 코드 되돌림은 필요 없다.

## 계약 변경

없음.

| 메서드 | 경로 | 유지할 동작 |
|---|---|---|
| `POST` | `/jobs` | multipart `file`, `202 {job_id, status: QUEUED}` |
| `GET` | `/jobs/{id}` | `job_id`, `status`, `highlights`, `error`, `precheck` 유지 |
| `GET` | `/jobs/{id}/video` | 완료 영상 200, 완료 전 또는 프리체크 탈락 409 유지 |
| `GET` | `/health` | `200 {status: ok}` 유지 |

상태 전이도 `QUEUED → PROCESSING → DONE | FAILED` 그대로다. 워커 수와 배치 크기는 API 응답에
추가하지 않는다. 인메모리 저장소의 재시작 후 작업 유실 한계도 이번 범위에서는 바꾸지 않는다.

## 검증 시나리오

| 단계 | 실행 및 기대 결과 |
|---|---|
| 로컬 파이프라인 | `AI_BATCH_SIZE=4 ./.venv/bin/python bench.py --smoke`. 나누어떨어지지 않는 마지막 배치를 포함해 프레임 수와 순서, 기존 블러 및 프리체크 검증이 통과한다 |
| 로컬 API | `AI_WORKERS=2 AI_BATCH_SIZE=4 ./.venv/bin/python server.py --smoke`. 정상 2건은 모두 `DONE`, 손상 입력만 `FAILED`이며 기존 404와 409 계약이 유지된다 |
| 기준선 | 전용 t3.small의 워커 1, 배치 1에서 `crowd` 29초 단일 3회와 동시 6건을 측정한다 |
| 배치 선택 | 워커 1에서 배치 2와 4를 각각 3회 측정한다. 20% 단축과 검출 동등성을 만족한 가장 작은 값을 고른다 |
| 워커 선택 | 워커 2와 채택 배치로 동시 6건을 실행해 처리량, 처리 시간, 메모리, 스왑, 재시작, 결과 영상을 확인한다 |
| 배포 | `plates` 30초 실영상 2건을 동시에 제출한다. 둘 다 `DONE`이고 내려받은 H.264 영상을 `ffprobe`로 읽을 수 있어야 한다 |

검출 동등성은 `crowd`, `plates`, `kr-faces`, `kr-plates`에서 영상당 30프레임을 뽑아 얼굴과 번호판을
따로 비교한다. `face_experiment.py`의 `iou()`와 기존 `sample_frames()`를 재사용하며, 배치 1 상자의
상대 recall이 각각 1.000이어야 한다. 한국 클립은 `samples/`에만 두고 커밋하지 않는다.

`scripts/ec2-ai-load-test.sh`는 상태를 2초마다, 메모리와 스왑 사용량, swap-in, swap-out, load1을
10초마다 기록한다. 작업별 처리 시간은 최초 `PROCESSING` 관측부터 `DONE`까지 계산하고 큐 대기 시간은
따로 남긴다. Docker `RestartCount`, `OOMKilled`, 결과 파일 크기와 `ffprobe` 결과도 기록한다.

시험 전후 CloudWatch의 `CPUUtilization`, `CPUCreditBalance`, `CPUSurplusCreditBalance`,
`CPUSurplusCreditsCharged`를 같은 구간으로 조회한다. 인스턴스, gp3, EIP, CPU 크레딧 비용은
`results/MSG-339-report.md`에 나눠 적는다.

판정 순서는 워커 1/배치 1, 워커 1/배치 2, 워커 1/배치 4, 워커 2/채택 배치다. 배치 후보가 단일
시간과 검출 기준을 통과하지 못하면 워커 2로 넘어가지 않는다. 워커 2가 처리량, 동시 처리 시간,
메모리, 스왑, 안정성 중 하나라도 실패하면 워커 1, 배치 1로 롤백하고 실패 결과도 남긴다.

## 작업 로그 (2026-08-07)

### 구현과 인프라

- `bench.py`에 최대 4프레임 배치와 마지막 불완전 배치 처리를 넣고, `server.py`는 한 프로세스에서
  워커를 최대 2개 시작하도록 바꿨다. 허용하지 않은 설정값은 모듈을 불러올 때 거부한다.
- 서울 리전 `ap-northeast-2a`에 전용 t3.small을 만들었다. 루트 볼륨은 암호화한 gp3 20GB이고
  `/swapfile` 2GB를 재부팅 후에도 다시 올리도록 설정했다.
- 8000 포트는 BE 보안 그룹에서 오는 요청만 허용했다. GitHub 호스팅 러너의 주소가 고정되지 않아
  22 포트는 공개했지만 SSH 키 인증만 남기고 비밀번호 인증과 root 로그인을 막았다.
- cloud-init에서 `/run/sshd`가 생기기 전에 `sshd -t`가 실행돼 초기 상태가 `error`로 남았다.
  디렉터리를 만든 뒤 설정 검증과 SSH 재적재를 직접 통과시켰다.
- GitHub Actions의 `DEV_EC2_HOST`를 새 EIP로 바꾸고, BE의 `AI_BASE_URL`은 새 사설 주소로 바꿨다.
  BE가 200을 응답하고 새 AI `/health`를 읽는 것을 확인한 뒤 기존 BE 인스턴스의 AI 컨테이너를
  중지했다. 기존 컨테이너 종료 코드는 137이었지만 Docker `OOMKilled`는 `false`였다.

### 채택 판정

- 단일 3회 중앙값은 배치 1이 180.53초, 배치 2가 188.37초, 배치 4가 187.64초였다. 배치 후보가
  각각 4.34%, 3.94% 느려 20% 단축 기준을 통과하지 못했다.
- 배치 2와 4 모두 얼굴 710개, 번호판 51개 상자를 빠짐없이 맞췄지만 속도 게이트가 먼저 실패했다.
  스펙의 판정 순서에 따라 워커 2 부하는 실행하지 않았다.
- 배포값과 롤백값은 `AI_WORKERS=1`, `AI_BATCH_SIZE=1`로 확정했다. 동시 6건과 비용을 포함한 원자료는
  `results/MSG-339-report.md`에 남겼다.

|---|---|
| 데이터 저장 | 잡 상태는 프로세스 메모리의 `jobs`, 대기는 `queue.Queue`, 업로드와 결과는 `JOBS_DIR/{job_id}`에 둔다. 재시작 후 복구는 이번 범위 밖이다 |
| DB와 Redis | AI 서버는 DB나 Redis를 읽지 않는다. BE와 기존 HTTP 계약으로만 통신한다 |
| 예외 흐름 | 워커가 `Exception` 또는 `SystemExit`을 잡아 해당 잡의 `error`를 채우고 `FAILED`로 바꾼다. 다른 워커와 잡 상태는 건드리지 않는다 |
| 실행 경계 | 모듈을 불러올 때 설정값만큼 데몬 스레드를 시작한다. uvicorn 프로세스는 하나이며 별도 스케줄러나 executor는 없다 |
| 임시 파일 | 작업 중간의 다운스케일본과 무음 블러본은 `TemporaryDirectory`에 두고 작업이 끝나면 지운다. 최종 H.264만 잡 디렉터리에 남는다 |

## 미해결 질문

없음. 배치 2와 4, 워커 2의 채택 여부는 위 EC2 실측 기준으로 판정한다.

[^1]: 워커 스레드는 큐에서 작업을 꺼내 처리하는 실행 단위다. Ultralytics는 여러 스레드가 하나의 YOLO 인스턴스를 공유하면 내부 상태 경합이 생길 수 있어 [스레드별 전용 모델](https://docs.ultralytics.com/guides/yolo-thread-safe-inference/)을 권장한다.
[^2]: 배치 추론은 여러 프레임을 모델 호출 한 번에 전달하는 방식이다. Ultralytics는 [이미지 목록을 입력하고 같은 순서의 결과 목록을 받는 호출](https://docs.ultralytics.com/modes/predict/)을 지원한다.
[^3]: OOM은 사용 가능한 메모리가 부족해 운영체제나 런타임이 프로세스를 종료하는 상태다. 이 티켓에서는 Docker의 `OOMKilled`와 컨테이너 재시작 횟수로 확인한다.
[^4]: IoU는 두 검출 상자가 겹친 면적을 합집합 면적으로 나눈 값이다. 여기서는 0.5 이상이면 배치 1과 후보 배치가 같은 대상을 찾았다고 본다.
[^5]: CPU 크레딧은 t3 계열이 기준 CPU 성능을 넘겨 쓸 때 소모하는 값이다. 잔액이 바닥난 뒤 버스트를 계속 쓰면 추가 비용이나 성능 제한이 생길 수 있어 처리량과 함께 기록한다.
[^6]: FIFO는 먼저 들어온 작업을 먼저 꺼내는 큐다. 워커가 둘이면 꺼내는 순서는 유지되지만 완료 순서까지 같지는 않다.
