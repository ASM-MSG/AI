# MSG-353: 하이라이트 전용 선분석 잡과 구간 품질 보정

> 요구사항 정본: BE 레포 `docs/prd/MSG-351-prd.md` (상태: 검토됨, 2026-08-10 성민 승인).
> BE와 AI 두 레포에 걸친 기능의 공유 PRD이고, AI 몫의 분해가 이 티켓이다 (PRD 결정 기록 참조).
> 이 문서는 그 PRD의 FR에 구현 방법만 붙인다. 내용이 어긋나면 PRD가 이긴다.

## 개요

블러 추론 없이 하이라이트 구간만 계산하는 동기 엔드포인트 `POST /highlights`를 추가한다.
업로드 위저드가 확정 전 원본에 대해 추천 구간을 수 초 안에 받아야 하는데(BE MSG-351이 소비),
현재 하이라이트는 블러 파이프라인(약 3분, YOLO 추론이 약 90%) 안에서만 나온다. 하이라이트
계산 자체는 실측 3~5초다(30초 1080p, `results/MSG-142-report.md` 계열 stage 분해).

같이, 구간 산출 품질을 보정한다. 현재 `detect_highlights`는 장면 길이를 그대로 쓰고 장면이
없으면 균등 3분할이라, 짧은 영상에서 5초 미만 구간과 좁은 시작점 간격이 나온다. FE 노출
티어의 근거(후보끼리 절반 이상 겹치면 가짜 선택)를 지키도록 최소 5초 창과 시작점 간격 규칙을
넣는다. 산출 로직은 한 곳이라 블러 파이프라인의 저장 하이라이트에도 같은 품질이 적용된다.

## 성공 기준

| 항목 | 판정 기준 |
|---|---|
| 전용 잡 | `POST /highlights`(multipart)가 큐를 거치지 않고 `{"highlights": [[시작초, 끝초], ...]}`를 동기 반환한다 |
| 구간 품질 | 각 구간 길이 5초 이상, 구간 시작점끼리 5초 이상 간격, 최대 3개. 조건을 지키며 3개를 못 채우면 개수를 줄인다 |
| 경계 | 5초 미만 영상은 `{"highlights": []}` (기존 `duration >= 5` 경계 유지) |
| 순서 | 배열 순서 = 추천 우선순위 (장면 랭킹 상위 먼저). MSG-350에서 계약으로 승격된 규약과 정합 |
| 실패 | 열 수 없는 입력은 422. 잡 상태를 만들지 않으므로 실패가 서버에 아무것도 남기지 않는다 |
| 파이프라인 회귀 | 기존 `/jobs` 블러 경로의 계약(최대 3구간, 탈락 잡 `[]`)이 그대로다. 저장 구간의 품질만 새 규칙을 따른다 |
| 검증 | `bench.py --smoke`가 구간 품질 규칙을, `server.py --smoke`가 `/highlights` 왕복을 태운다 |
| 성능 | EC2 실측(`scripts/ec2-bench.sh` 계열)으로 30초 1080p 왕복이 블러 파이프라인의 highlight 단계 실측(2.9~4.7초)과 같은 자릿수임을 확인한다. 4K와 3분 상한 케이스도 함께 실측해 기록한다 |

## 설계 결정

### D-1: 전용 잡은 동기 엔드포인트다 (큐 우회)

PRD FR-7(블러 잡 처리 중에도 지연 목표 유지)의 이행. 선분석은 YOLO 모델이 필요 없어 워커
큐에 넣을 이유가 없다. FastAPI의 동기 핸들러는 스레드풀에서 돌아 이벤트 루프를 막지 않고,
잡 상태·잡 디렉터리·폴링·정리가 전부 불필요해진다 (`tempfile`이 수명 관리). 인메모리 잡
저장소 유실 문제(재시작)에서도 자유롭다.

블러 잡이 CPU를 쓰는 동안의 경합으로 3~5초가 다소 늘어날 수는 있다. 큐 대기(최대 3분)를
없애는 것이 본질이고, 경합 폭은 EC2 실측으로 확인한다.

### D-2: 다운스케일 재인코딩은 하지 않는다

PRD FR-5의 취지는 고해상도 원본이 지연 목표를 깨지 않게 하는 것이다. ffmpeg 재인코딩
다운스케일은 원본을 디코딩하고 다시 인코딩한 뒤 축소본을 또 디코딩하므로, 원본을 한 번
디코딩하고 감지용 프레임만 내부 축소하는 직분석보다 항상 비싸다. PySceneDetect[^1]는
감지 프레임을 자체 다운스케일하므로 그쪽에 맡긴다.

4K가 느린 실측(30.9초)의 원인은 감지가 아니라 4K 프레임 디코딩이고, 디코딩은 생략할 수
없다(`grab()`도 디코딩은 한다. CLAUDE.md "알아둘 함정"). 그래서 4K 장편의 최악 지연은
소프트웨어로 못 줄인다. EC2 실측으로 수치를 확정하고, 목표를 크게 벗어나면 상한 정책
강화(BE FR-8에 해상도 축 추가)를 후속 티켓으로 올린다.

### D-3: 구간 품질 규칙 (`detect_highlights` 개편, 파이프라인 공유)

상수는 `bench.py` 상단에 근거와 함께 둔다: `HIGHLIGHT_MIN_SEC = 5.0`,
`HIGHLIGHT_MIN_GAP_SEC = 5.0` (근거: FE 길이별 노출 티어, BE `docs/prd/MSG-351-prd.md` FR-3).

1. **후보 생성**: 장면 전환 감지 결과를 길이 내림차순으로 랭킹(현행 유지). 각 장면을 창으로
   정규화한다. 길이가 5초 미만이면 장면 시작점부터 5초 창(영상 끝을 넘으면 시작점을 앞으로
   당김), 5초 이상이면 그대로 둔다.
2. **탐욕 선택**: 랭킹 순서대로, 이미 뽑힌 구간들과 시작점 간격이 5초 이상인 것만 최대
   3개까지 채택한다.
3. **그리드 보충**: 3개를 못 채우면 균등 그리드 후보로 보충한다. `n = min(3, duration // 5)`개의
   5초 창을 균등 배치하면 간격이 수학적으로 5초 이상 보장된다 (`duration >= 5n`이라
   `(duration - 5) / (n - 1) >= 5`). 그리드 후보도 기존 채택분과의 간격 규칙을 통과해야 한다.
   장면이 0개면(고정 촬영) 그리드만 남는다. 기존 균등 3분할 폴백의 대체다.
4. 반환은 채택 순서(우선순위) 그대로, 초는 소수점 둘째 자리 반올림.

12초 영상이면 그리드가 5초 창 2개(시작점 0초, 7초), 6초 영상이면 1개가 된다. 기존 균등
3분할이 12초에서 4초짜리 3개를 만들던 문제가 사라진다.

### D-4: 5초 미만 경계와 상한 검증

`duration < 5`는 빈 배열이다(현행 경계 유지, `/highlights`도 동일). 원본 3분 상한 검증은
BE 몫이다(PRD FR-8, 1차는 FE 선택 차단이고 방어선은 BE). AI는 내부 통신 전용이라 받은 입력을
그대로 분석한다.
