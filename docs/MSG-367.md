# MSG-367: AI 파이프라인 전체 프레임 인코딩 3회를 1회로 줄이기

> PRD 면제 티켓 (CLAUDE.md "개발 파이프라인" 면제 기준: 성능·구조 개선, 요구사항 불변).
> 같은 재생본(블러 + 하이라이트 + 원본 오디오, h264)을 더 적은 인코딩 단계로 만드는 내부
> 개선이라 제품 요구사항을 새로 만들거나 바꾸지 않는다. 요구사항 정본은 Jira MSG-367 티켓
> 본문(2026-08-10 성민 작성)이고, 이 문서는 거기에 "어떻게"만 붙인다.

## 개요

영상 한 건이 재생본이 되기까지 전체 프레임 인코딩이 4번 돈다. BE `FfmpegRunner.encode720p()`가
1번(패스 1), 이 레포가 3번(패스 2~4)이다. 이 티켓은 레포 안의 3번을 1번으로 줄인다.
패스 1은 남긴다 — BE의 720p 정규화가 AI 서버의 디코딩 비용 상한을 지키는 장치라서다.

| 패스 | 위치 | 현행 동작 | 코덱 |
|---|---|---|---|
| 2 | `server.py:downscale()` | 필터(`max(w,h) > 1920` 스케일, `fps > 30` 감쇠)가 하나도 안 걸려도 무조건 재인코딩 | libx264 + aac |
| 3 | `bench.py:run()`의 `cv2.VideoWriter` | 블러 프레임을 무음으로 기록 | mp4v[^1] |
| 4 | `server.py:process()`의 병합 ffmpeg | 패스 3 결과를 다시 굽고 오디오를 붙임 | libx264 + aac copy |

**화질이 이유다. 속도가 아니다.** 사용자가 보는 재생본은 4세대 인코딩본이고 중간에 mp4v를
한 번 경유한다 — 파이프로 합치면 이 세대 손실[^2]이 한 겹 사라진다. 속도 기대치는 낮게
잡는다: 1080p 기준 추론(얼굴 39~44% + 번호판 38~43%)이 지배적이고 재인코딩은
5~9%(4K는 24%)다 (`results/MSG-142-report.md` 단계별 비중). 2026-07-25 멘토 리뷰의
"이중 인코딩 제거" 지시에 대한 응답이며, 나머지 절반인 "검출을 저해상도 프록시로"는 실측으로
이미 닫혔다 — ms/frame이 해상도와 무관하고(`imgsz=640` 리사이즈), imgsz 하향은 작은 얼굴
64~91% 미탐이다 (`results/MSG-281-report.md`, CLAUDE.md "알아둘 함정").

## 성공 기준

티켓 완료 조건 4개를 판정 가능한 기준으로 옮긴다. 성능 수치는 EC2 실측만 유효하다
(macOS 측정 무효 — CLAUDE.md "알아둘 함정").

| 티켓 완료 조건 | 판정 기준 |
|---|---|
| AI 레포 안 전체 프레임 인코딩 1회 | BE 정규화 경로(긴 변 ≤ 1920 · ≤ 30fps 입력)에서 인코딩이 rawvideo 파이프[^3] 1회다. 판정: `server.py --smoke`가 720p 30fps 합성 입력에 `downscale()` 바이패스(반환 경로 = 입력 원본)를 어서션하고, 중간 산출물 `raw.mp4` 경로가 코드에서 사라진다. 비정규 입력(> 1920 또는 > 30fps)만 방어용 다운스케일 1회가 추가된다 — 패스 1을 남기는 것과 같은 이유의 안전장치 |
| 재생본에 mp4v 경유 흔적이 없다 | 결과 mp4의 비디오 코덱이 ffprobe[^4] 기준 `h264`다(`mpeg4` 아님). 판정: `bench.py --smoke`·`server.py --smoke`에 ffprobe 코덱 어서션 추가 + 배포 E2E(`scripts/ec2-deploy.sh`)의 기존 H.264 검사 유지 |
| 블러 품질·탐지 결과가 변경 전과 같다 | 같은 입력 전/후로 `run()` 리포트의 `detections`(face·plate)와 출력 프레임 수가 동일하다. 추론·블러 코드는 안 건드리므로 남는 위험은 프레임 유실·순서 어긋남이고, 기존 smoke의 "출력 프레임 수 = 입력" 어서션과 순서 프로브(MSG-339)가 잡는다. 실영상 대조는 `crowd`·`plates` + 한국 번호판 클립(`kr-plates`) — 번호판 결함이 드러나지 않는 조합 함정을 피한다(CLAUDE.md "알아둘 함정"). 기능 판정이라 macOS 허용 |
| 건당 처리 시간이 나빠지지 않았다 | dev EC2에서 같은 입력의 API 왕복(`POST /jobs` → `DONE`) 3회 중앙값이 변경 전 이하다. 피크 메모리도 함께 기록해 동시 실행되는 ffmpeg 인코더가 스왑을 부르지 않는지 확인한다(t3.small 2GB, 변경 전 파이썬 피크 503.7MB — `results/MSG-339-report.md`). 결과는 `results/MSG-367-report.md` |

## 설계 결정

### D-1: 패스 2는 무필터면 건너뛴다

`downscale()`은 지금 스케일·fps 필터를 조건부로 붙이면서 `-c:v libx264 -c:a aac`는 무조건
붙인다. BE가 이미 720p로 정규화한 입력에는 두 필터가 안 걸리는데도 재인코딩만 하고 끝난다.

- 필터가 하나도 안 붙으면 ffmpeg를 실행하지 않고 **원본 경로를 그대로 쓴다**.
  `downscale(src, dst)`가 분석에 쓸 경로를 반환하도록 바꾸고(바이패스면 `src`, 필터를
  태웠으면 `dst`), `process()`는 반환 경로로 프리체크·`bench.run`을 태운다.
- 필터를 태우는 경우 `-an`을 붙여 오디오를 버린다. 다운스케일본은 프레임 분석에만 쓰이고
  최종 오디오는 항상 원본에서 가져오므로(D-3), 여기서 aac 인코딩은 버려질 결과물이다.
- `-r 30` fps 감쇠는 영상 길이를 바꾸지 않으므로 원본 오디오와의 싱크는 유지된다.

### D-2: 패스 3과 4는 rawvideo 파이프 하나로 합친다

`run()`의 `cv2.VideoWriter`(mp4v·무음)를 ffmpeg 서브프로세스로 바꾼다. 블러된 BGR 프레임을
표준입력으로 흘리고, 오디오 원본을 두 번째 입력으로 물려 최종 재생본을 한 패스로 굽는다.

```text
ffmpeg -y -f rawvideo -pix_fmt bgr24 -s {w}x{h} -r {fps} -i pipe:0
       -i {audio_src} -map 0:v -map 1:a?
       -c:v libx264 -preset veryfast -pix_fmt yuv420p -c:a aac -shortest {out}
```

- `-pix_fmt yuv420p`[^5]를 명시한다 — bgr24 입력을 그대로 두면 재생 호환성이 떨어지는
  픽셀 포맷으로 인코딩될 수 있다.
- fps는 cv2가 읽은 **원본 값 그대로** 넘긴다(29.97 등 소수 유지). 반올림하면 A/V 싱크가
  영상 길이에 비례해 밀린다.
- `run()` 시그니처는 `run(path, device, out_path, audio_src=None)`로 확장한다. 기본값
  `None`이면 입력 `path`를 오디오 원본으로 쓴다(단독 CLI 실행도 무음 mp4v 대신 오디오 있는
  h264를 얻는다). `process()`는 `audio_src=src`(잡 원본)를 명시한다 — 다운스케일을 탔으면
  분석 입력에 오디오가 없기 때문(D-1).
- `process()`의 병합 ffmpeg 호출과 중간 파일 `raw.mp4`는 삭제한다. `run()`의 출력이 곧
  최종 재생본 `out.mp4`다.
- 인코딩이 추론과 동시에 진행된다(ffmpeg가 파이프에서 도착하는 대로 인코딩). 인코더가
  밀리면 파이프 쓰기가 블록되는 자연 배압이고, 그 대기는 기존 `stages.encode` 항목에
  잡힌다. **`encode` 수치의 의미가 "mp4v 기록"에서 "파이프 쓰기 + 배압 대기"로 바뀌므로**
  변경 전 리포트의 stage 비중과 직접 비교하지 않는다 — 전후 비교는 API 왕복 시간으로 한다
  (검증 계획).

### D-3: 오디오는 항상 원본에서, 없으면 무음

- 오디오 스트림 매핑은 현행 병합 패스와 같은 `-map 1:a?`다 — `?`가 오디오 없는 입력(합성
  smoke 영상, 무음 촬영본)을 에러 없이 무음 재생본으로 만든다.
- 오디오는 `-c:a aac`로 인코딩한다. 현행도 패스 2에서 aac로 한 번 인코딩하므로 AI 레포 안
  오디오 인코딩 횟수는 그대로 1회고, 원본이 aac가 아닌 경우에도 mp4 컨테이너와 안전하다
  (copy로 바꾸면 비 aac 원본에서 병합이 깨질 수 있다).
- `-shortest`로 영상보다 긴 꼬리 오디오를 자른다 — 컨테이너 메타 오차로 오디오가 수십 ms
  긴 흔한 경우에 재생 길이가 늘어지는 것을 막는다.

### D-4: 파이프 실패는 잡 FAILED로 드러낸다

`cv2.VideoWriter`는 실패해도 조용하다(빈 파일). 파이프판은 실패가 감지 가능해진다 — 감지한다.

- 프레임 루프 종료 후 `stdin.close()` → `wait()` → 반환 코드 검사. 0이 아니면 ffmpeg
  stderr를 담아 예외를 던진다. 도중 `BrokenPipeError`(ffmpeg 조기 사망)도 같은 경로다.
- 예외는 기존 워커의 `except (Exception, SystemExit)`가 받아 잡을 `FAILED`로 만들고
  `error`에 사유가 남는다 — 계약 변경 없음.
- 열리지만 프레임이 0장인 입력은 현행은 빈 mp4v 파일이 "정상 완료"됐다. 파이프판은 ffmpeg가
  빈 비디오 입력으로 실패해 `FAILED`가 된다 — 손상 입력이 성공으로 위장하던 구멍이 닫히는
  의도된 변화다.
- 프리체크 탈락 경로는 `run()` 전에 반환하므로 영향 없다(out.mp4 미생성 = 원본 유출 차단
  유지, MSG-284 FR-6).

## 검증 계획

테스트 프레임워크를 도입하지 않고 기존 `--smoke` 확장 + 실측 리포트로 한다
(`.claude/rules/project-conventions.md` 검증 관행).

1. **`bench.py --smoke`** — 변경 지점 표의 어서션 추가분 포함 green. 오디오 검증용 합성
   영상은 기존 `make_smoke_video`에 lavfi 사인톤 옵션을 붙여 만든다(새 헬퍼 발명 금지).
2. **`server.py --smoke`** — 기존 4K 60fps 경로(필터 태움)와 새 720p 30fps 바이패스 경로를
   둘 다 태우고, 결과물 코덱·오디오를 ffprobe로 어서션. macOS에서는 기능 판정만 한다.
3. **탐지·블러 동일성 대조 (macOS 허용, 기능 판정)** — 변경 전/후 커밋에서 같은 실영상
   (`crowd`·`plates`·`kr-plates`)을 `bench.py`로 돌려 `detections` 수치와 출력 프레임 수가
   동일함을 기록한다. 블러 강도 회귀는 기존 smoke의 MSG-280 잔여 std 어서션이 지킨다.
4. **EC2 전후 실측 (`results/MSG-367-report.md`)** — **MSG-142 비중표는 `bench.run` 내부만
   계측해 `server.py`의 패스 2·4가 통째로 빠져 있다** (티켓 명시. 정황 근거: MSG-339에서
   `bench.run` 내부 중앙값 180.53초 vs API `PROCESSING` 중앙값 236.5초 — 단 후자는 동시
   6건 부하 중 측정이라 차이를 패스 2·4에 직접 귀속할 수 없다). 따라서 전후 비교는 stage
   비중이 아니라 **유휴 상태 API 왕복**으로 잰다:
   - 방법: 변경 전/후 각각, 같은 29초 `crowd` 입력을 `POST /jobs` → `DONE`까지 3회, 중앙값
     비교 (`scripts/ec2-bench.sh`·`scripts/ec2-ai-load-test.sh` 계열 활용).
   - 판정: 중앙값이 변경 전 이하(성공 기준 4행). 기대치는 낮다 — 인코딩 비중 5~15%라
     건당 수 초~수십 초 단축 수준.
   - 함께 기록: 피크 메모리·스왑(D-2의 동시 인코딩이 t3.small에서 스왑을 부르지 않는지,
     MSG-339 측정 방법 재사용), 결과물 ffprobe 코덱·오디오·프레임 수.
5. **배포 E2E** — `main` 머지 시 `scripts/ec2-deploy.sh`의 실영상 E2E(H.264 검사 포함)가
   그대로 초록불이어야 한다.

[^1]: mp4v(MPEG-4 Part 2): OpenCV `VideoWriter`가 쓸 수 있는 구세대 코덱. h.264(libx264)보다 압축 효율이 낮아 같은 화질에 파일이 크고, 여기서는 최종 재인코딩 전의 중간 산출물로만 쓰여 세대 손실만 보태고 있었다.
[^2]: 세대 손실: 손실 압축을 거듭할수록 화질이 단계마다 깎이는 현상. 이 문서의 결론 근거다 — 인코딩 패스를 합치는 이유가 속도가 아니라 이 손실을 한 겹 없애는 것이다.
[^3]: rawvideo 파이프: 압축하지 않은 프레임 바이트를 ffmpeg 표준입력으로 직접 흘리는 방식(`-f rawvideo -i pipe:0`). 중간 파일 없이 파이썬이 만든 프레임을 곧바로 최종 코덱으로 인코딩할 수 있다.
[^4]: ffprobe: ffmpeg에 딸린 미디어 검사 도구. 결과 파일의 코덱·스트림 구성을 기계 판정할 수 있어 "mp4v 흔적 없음"의 판정 도구로 쓴다.
[^5]: yuv420p: 재생기 호환성이 가장 넓은 픽셀 포맷. 명시하지 않으면 ffmpeg가 rawvideo 입력(bgr24)에 맞춰 일부 재생기가 못 여는 포맷을 고를 수 있다. 기존 `make_smoke_video`도 같은 이유로 명시한다.
