# Subagent Orchestration — 에이전트 팀 운영 원칙

여러 서브에이전트를 팀으로 조율하는 모든 스킬(현재 spec-driven-dev)에 적용되는 공통 원칙.
스킬 문서는 "무엇을 시키는지"(단계 라우팅)만 담고, "어떻게 팀을 굴리는지"는 이 규칙을 따른다.

## 팀 구성 방식

**이 환경의 실제 도구 기준**: `TeamCreate`/`TeamDelete` 도구는 없다. 이름을 지정해
`Agent(run_in_background: true)`로 스폰하면 그 이름이 곧 팀원 식별자가 되고, `SendMessage`로
이름을 주소로 서로/리더와 통신할 수 있다. 팀 구성은 "이름 붙여 스폰"으로 대체하고,
조율은 `TaskCreate`/`TaskUpdate`/`TaskGet`(공유 작업 보드) + `SendMessage`(실시간 소통)로 한다.

- 작업 등록 시 각 작업에 `owner`를 팀원 이름으로 지정한다. 검증(리뷰) 작업은 대응하는 개발
  작업에 `addBlockedBy`로 의존시킨다 — 개발이 끝나야 리뷰가 의미 있으므로.
- `Agent` 호출에 `model`을 지정하지 않는다 — 세션 모델을 그대로 상속한다.
  에이전트 정의 프런트매터와 호출부 **양쪽 다** 생략해야 상속이 동작한다
  (BE 하네스에서 확정된 원칙 — 정의 쪽 `model`이 남아 있으면 호출부 생략 시 정의 값이 적용된다).

## 조율 원칙

- **점진적 QA**: 개발 에이전트는 모듈을 완성하면 `TaskUpdate`로 상태를 갱신하고 즉시 리뷰
  담당에게 `SendMessage`로 리뷰를 요청한다 — 전체 완료를 기다리지 않는다.
- **리뷰어 상주**: 리뷰 담당 에이전트는 개발 에이전트와 동시에 살아있어야 한다(항상 스폰).
- **경계면 합의 우선**: 도메인 간 계약·API 스키마(BE↔AI HTTP 계약 등) 변경이 필요하면 관련
  에이전트끼리 `SendMessage`로 먼저 합의한다. 합의가 안 되면 양쪽 주장을 병기해 사용자 판단으로
  올린다 — 리더가 임의로 한쪽을 지우지 않는다. **레포 경계를 넘는 계약(BE가 소비하는 엔드포인트·
  응답 필드)은 이 레포 안에서 합의가 끝나지 않는다** — 반드시 사용자 판단으로 올린다.
- **1회 수정 후 에스컬레이션**: 리뷰 위반은 담당 에이전트에게 직접 전달하고 1회 수정 기회를
  준다. 재실패하면 리더에게 에스컬레이션한다. 같은 위반이 2회 반복되면 개별 에이전트 문제가
  아니라 스펙-컨벤션 충돌 가능성을 의심하고 사용자에게 확인한다.
- **리더는 감독만**: 리더(오케스트레이터)는 유휴 알림을 받으면 `TaskGet`으로 진행 상황을
  확인하고 막힌 팀원에게만 `SendMessage`로 개입한다. 리더가 코드를 직접 짜서 팀원 작업과
  워킹트리에서 경합하지 않는다.

## 검증 실패 · 결함 처리 루프

검증(`--smoke`·실험 스크립트·실측)이 깨지거나 결함이 나오면 손으로 즉흥 수정하지 않고 루프를 돈다:

1. **디버깅 포인트 확보** — 실패 로그·재현 명령을 먼저 남긴다.
2. **원인 리뷰** — 리뷰 담당(또는 리더)이 원인을 특정한다. 증상 패치 금지.
3. **수정 구현** — 담당 개발 에이전트가 고친다 (리더 대리 수정 금지).
4. **검증 재실행** — green 확인 후에만 완료 처리.

코드리뷰(reviewer) + 교차 리뷰(Codex 등 정적 분석층)를 통과한 변경만 완료로 친다.

## 커밋 흐름

커밋 실행은 항상 사용자 몫이다 — 에이전트 팀은 커밋/푸시하지 않는다. 모듈 green + 리뷰 통과
시점마다 커밋 포인트를 알리고 사용자 응답까지 새 단계 착수를 보류한다. 세부(스톱 게이트,
알림 타이밍): `.claude/skills/spec-driven-dev/references/commit-gate.md`.
