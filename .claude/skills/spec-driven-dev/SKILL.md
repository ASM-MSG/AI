# Spec-Driven Dev Orchestrator

`docs/MSG-XXX.md` 스펙을 읽고 ai-developer / convention-reviewer 팀을 조율해 실제 코드와
검증(`--smoke`·실측)을 완성하는 오케스트레이터.

팀 운영 방식(이름 붙여 스폰, `SendMessage` 통신, `TaskCreate` 작업 보드, 점진적 QA,
에스컬레이션, 검증 실패 루프, `model` 미지정)은 공통 규칙
`.claude/rules/subagent-orchestration.md`를 따른다. 이 문서는 단계 라우팅만 담고,
무거운 단계별 절차는 그 단계에 **도달했을 때** `references/`에서 읽는다 — 미리 다 읽지 않는다.

## 에이전트 구성

| 팀원 이름 | 에이전트 타입 | 역할 | 산출물 |
|-----------|--------------|------|--------|
| `spec-writer` | `spec-writer` | 스펙 문서 없을 때만 선행 호출 | `docs/MSG-{번호}.md` |
| `ai-dev` | `ai-developer` | 파이썬 구현 (파이프라인·서버·실험 스크립트) | `bench.py`·`server.py`·`scripts/**`, `--smoke` 경로, `results/MSG-XXX-report.md` |
| `reviewer` | `convention-reviewer` | 컨벤션·스펙 일치·검증 실행 | 리뷰 결과(위반 목록 또는 통과) |

`prd-writer`는 이 표에 없다 — 서브에이전트가 아니라 **인라인 스킬**이다(PRD의 입력이 대화에 흐르는
맥락이라 격리하면 품질이 떨어진다). Phase 0 게이트에서 `Skill` 도구로 직접 실행한다.

## 워크플로우

### Phase 0: 컨텍스트 확인

0. **PRD 게이트 (필수, 건너뛰기 금지)**: 이 티켓을 **커버하는 PRD**의 존재를 **스펙보다 먼저** 확인한다.
   **판별 전에 티켓 맥락부터 확보한다** — 기존 스펙(`docs/MSG-{번호}.md`)·대화에 없으면 Jira 조회.
   공유 PRD 지목("선행 정본: ..." 문구)이 그 맥락 안에 있어서, 맥락 없이 판별하면 커버되는 티켓을
   "PRD 없음"으로 오판해 중복 PRD를 만든다.
   판별 순서 — ① 전용 `docs/prd/MSG-{번호}-prd.md` ② 확보한 맥락(스펙·대화·티켓)이 정본으로
   지목하는 **공유 PRD**(부모 기능 PRD에 이 티켓 범위가 실제로 들어 있는지 확인하고, 없으면
   커버로 인정하지 않는다) ③ 티켓 전 아이디어 단계의 `docs/prd/{kebab-slug}.md`.
   게이트를 통과하면 **그 실제 경로**를 이후 단계에 넘긴다.
   파이프라인은 PRD → 스펙 → 구현이고, PRD가 빠지면 "무엇을 왜 만드는지"가 스펙 작성자의 즉석
   판단으로 대체된다.
   - **있음** → 먼저 PRD 헤더의 `상태:`를 본다. 판정은 **`상태:` 뒤 첫 토큰(공백 전까지)이
     `초안`/`검토됨`/`확정` 중 하나와 정확히 일치하는가**로 한다 — 공백 뒤 부연(괄호 메모·날짜,
     예: `검토됨 (2026-07-29 기획 확정 반영)`)은 무시하되, `검토됨아님`처럼 붙여 쓴 변형은
     일치가 아니다. **헤더가 없거나 첫 토큰이 세 값 어느 것도 아니면 `초안`으로 취급한다**
     (fail-closed — 판별 불가가 통과가 되면 필수 게이트가 아니다).
     **`초안`이면 승인 전이다** — 존재가 승인이 아니다
     (이전 세션이 만들어놓고 승인 못 받은 채 끝났을 수 있다). 신규 생성 흐름과 **동일한 절차**를
     밟는다: 요약·미해결 질문을 보고하고, **미해결 질문이 남아 있으면 답을 PRD에 반영한 뒤**
     명시적 승인을 받아 헤더를 `검토됨`으로 갱신하고 진행한다 — 질문을 남긴 채 `검토됨`으로
     올리지 않는다. `검토됨`/`확정`이면 그대로 진행.
     대조는 스펙의 결정·API·처리 정책이 PRD의 FR/비기능과 모순되는지,
     그리고 **PRD의 미해결 질문을 스펙이 임의로 확정하지 않았는지**를 본다 — 판단이 애매하면
     어긋남으로 취급한다(거짓 "일치" 판정이 낡은 요구사항을 구현시키는 것보다 한 번 더 묻는 쪽이
     싸다). 단 **스펙과 PRD가 어긋나면 조정 전에는 Phase 1로 못 간다** —
     어긋난 지점을 요약해 사용자에게 어느 쪽이 정본인지 확인받고, ⓐ PRD가 정본이면 spec-writer를
     재호출해 스펙을 갱신한 뒤(그 결과로 진행) — 재호출 프롬프트에 **"사용자가 스펙 갱신을 이미
     승인함"을 명시**한다(에이전트의 기존 스펙 덮어쓰기 확인을 건너뛰는 신호 — 안 넣으면 방금
     받은 확인을 또 묻는 이중 확인이 된다. 재생성 결과에 **미해결 질문이 있으면 해소 전에는
     Phase 1로 못 간다** — 방금 조정한 스펙이 모호함을 안고 구현에 넘어가면 조정이 무의미) ⓑ 스펙 쪽 내용이 옳다고 판정되면 **그 내용을 PRD에
     반영해 PRD를 먼저 갱신**한 뒤 진행한다 — 정본 지위는 항상 PRD다(스펙이 정본이 되는 게 아니라,
     낡은 PRD를 현실에 맞게 고쳐 정본 자격을 회복시키는 것). 사용자의 "스펙 쪽이 옳다" 판정이
     그 갱신의 승인을 겸하므로 다시 묻지 않되, **갱신 diff 요약은 보고**하고 헤더는 `검토됨`을
     유지한다. 갱신이 판정받은 범위를 넘는 요구사항 변경으로 번지면 그건 새 변경이다 — `초안`으로
     내리고 재승인받는다. 낡은 쪽을 그대로 구현에 넘기면 사용자가 방금 기각한 요구사항이 구현된다.
   - **없음** → **먼저 면제 여부를 판단한다**(아래 면제 기준 — 순서 중요: 이 판단 전에 prd-writer를
     부르면 면제 티켓도 무조건 PRD를 만들게 된다). 면제면 근거 한 줄 알리고 PRD 없이 다음 단계로.
     면제가 아니면 `prd-writer` 스킬을 실행한다. **확인은 스톱 게이트고, 해제는 명시적 승인뿐이다**
     (커밋 게이트와 동일): 생성된 PRD 경로·핵심 요구 요약·미해결 질문을 사용자에게 보고하고
     보류한다. "진행해" 류 **승인**만 게이트를 연다 — 승인 즉시 PRD 헤더를 `상태: 검토됨`으로
     **정규화**해 영속화한다(리터럴 치환이 아니다 — 헤더가 없으면 새로 쓰고, 비정상 값이면
     교체한다. 판별이 초안 취급한 헤더는 승격도 같은 규칙으로 고쳐야 다음 세션이 읽는다).
     수정 지시는 반영 후 재승인, 미해결 질문은 답을 PRD에 반영한 뒤 재승인,
     **기각·보류·무응답은 해제가 아니다.**
     **스펙이 이미 있어도 PRD가 없으면 이 게이트를 통과한 게 아니다** — 스펙만 보고 바로
     구현에 들어가지 않는다(구 티켓 이어받기가 이 구멍으로 가장 자주 샌다).
   - **면제 기준** (위 "없음" 분기의 선판단에서 사용): CLAUDE.md "개발 파이프라인" 절이 단일 정본 —
     "이 작업이 제품 요구사항을 새로 만들거나 바꾸는가" 하나로 판단한다.
1. `docs/MSG-{번호}.md` 존재 여부 확인.
   - **없음** → **spec-writer 스킬을 실행한다**(에이전트 직호출 금지 — 맥락 확보·게이트·프롬프트
     조립·검증이 그 스킬 한 곳에 있고, 여기서 에이전트를 직접 부르면 그 계약이 복제·우회된다).
     게이트 0에서 이미 확인한 **실제 PRD 경로 또는 면제 근거**를 스킬에 전달해 중복 판별을
     생략시킨다. **스킬 결과에 미해결 질문이 있으면 해소 전에는 Phase 1로 못 간다**(조정 경로와
     동일 규칙 — 모호함을 안은 스펙을 구현에 넘기지 않는다). PRD도 티켓 설명도 없고 Jira 조회도
     안 되면 여기서 멈추고 되묻는다.
   - **있음, 첫 개발 요청** → Phase 1로 진행 (초기 실행).
   - **있음, "이어서/다시/일부만" 같은 후속 요청** → 관련 파일의 기존 코드를 `Grep`/`Read`로
     확인해 이미 구현된 부분과 남은 작업을 구분한다(부분 재실행). 이미 끝난 모듈은 재작업시키지 않는다.
2. `git status`로 미커밋 변경이 있는지 확인한다. 다른 작업 중인 변경이 있으면 사용자에게
   알리고 계속할지 확인한다 — 임의로 stash/reset하지 않는다.

### Phase 1: 팀 결정 (고정)

이 레포는 파이썬 단일 도메인이라 오너 판정이 없다. 팀은 항상 **`ai-dev` + `reviewer`** 고정이다.
`reviewer`는 항상 스폰한다(모듈 단위 점진적 리뷰를 위해 개발 에이전트와 동시에 살아있어야 한다).

스펙이 BE↔AI HTTP 계약(엔드포인트·응답 필드)을 건드리면 그건 레포 밖 소비자가 있는 변경이다 —
팀 안에서 합의하지 말고 사용자에게 먼저 확인한다.

### Phase 2: 스폰 및 작업 등록

```
Agent(name: "ai-dev", subagent_type: "ai-developer",
      run_in_background: true,
      prompt: "docs/MSG-{번호}.md 스펙을 읽고 구현하라. 스펙이 정의한 검증 명령으로 green을
               확인한 뒤에만 완료를 알려라. ...")

Agent(name: "reviewer", subagent_type: "convention-reviewer",
      run_in_background: true,
      prompt: "ai-dev가 모듈을 완성할 때마다 SendMessage로 리뷰 요청이 온다.
               .claude/rules/project-conventions.md 기준으로 검증하고, 스펙이 정의한 검증 명령
               (`python server.py --smoke` 등)을 실제로 실행해 확인하라.")
```

`TaskCreate`로 스펙의 "검증 시나리오"를 모듈 단위 작업으로 등록한다 — `owner` 지정과
리뷰 작업의 `addBlockedBy` 의존은 공통 규칙대로.

### Phase 3: 구현 (팀원 자체 조율)

- 조율(모듈 완성 → 즉시 리뷰 요청, 1회 수정 후 에스컬레이션)은 공통 규칙 그대로.
- **커밋 포인트 + 스톱 게이트 (필수)**: 모듈이 green + 리뷰를 통과하는 시점마다 발생한다.
  첫 커밋 포인트에 도달하기 전에 `references/commit-gate.md`를 읽고 그대로 적용한다.

### Phase 4: 통합 확인

1. 모든 개발 작업과 리뷰 작업이 `completed`인지 `TaskGet`으로 확인한다.
2. 리더가 직접 **스펙이 정의한 검증 명령**(`python bench.py --smoke`·`python server.py --smoke`·
   전용 실험 스크립트 등)을 1회 실행해 최종 확인한다(리뷰어의 부분 실행과 별개).
   성능·정확도 주장이 걸린 티켓이면 `results/MSG-{번호}-report.md`가 실제로 생성됐는지도 본다 —
   **macOS 성능 수치는 무효**라 EC2 실측이 필요한 티켓은 그 리포트가 완료 조건이다
   (CLAUDE.md "알아둘 함정" 절).
3. 실패가 남아있으면 담당 팀원에게 재작업을 요청한다. 스펙 자체의 결함으로 보이면 사용자에게
   보고하고 스펙 수정 여부를 확인한다 — 임의로 스펙을 재해석해 구현을 바꾸지 않는다.
4. **Codex 교차 리뷰**: 검증 green 후 `references/codex-review-loop.md`를 읽고 그대로 실행한다.
   필수 게이트는 3번까지고 Codex는 추가 검증층이지만, 백그라운드 서브에이전트가 짠 코드를 보는
   유일한 실질 diff 리뷰다 — 임의 생략·생략 위장 금지.

### Phase 5: 마무리

`references/finalize.md` 체크리스트대로: 요약 보고 → CLAUDE.md "현재 상태 · 다음 작업" 절 갱신 →
스펙 문서에 작업 로그 append → 커밋 메시지 제안(실행은 사용자) → 팀원 종료 통지.

## 에러 핸들링

| 상황 | 전략 |
|------|------|
| 개발 에이전트 실패/중단 | 리더가 유휴 알림 수신 → `SendMessage`로 상태 확인 → 재시작. 재실패 시 완료 처리하지 않고 남은 범위를 보고서에 명시 |
| 최종 검증(`--smoke` 등) 실패 | 실패 로그 핵심부를 사용자에게 보여주고, 완료 처리하지 않음 |
| 모델 가중치·의존성 문제로 로컬 검증 불가 | 원인을 보고하고 EC2 검증으로 대체할지 확인 — "돌려봤다" 위장 금지 |

반복 위반 에스컬레이션은 공통 규칙(`subagent-orchestration.md`)의 조율 원칙을 따른다.

확인 → `ai-dev` + `reviewer` 스폰 → 모듈별 점진적 리뷰 → `python server.py --smoke` 통과 →

**PRD 게이트 흐름**: "MSG-170 개발 시작해줘", 스펙은 있는데 `docs/prd/MSG-170-prd.md`가 없음 →

**면제 흐름**: "MSG-171 개발 시작해줘 — Dockerfile 베이스 이미지 보안 패치 버전업" → 제품
