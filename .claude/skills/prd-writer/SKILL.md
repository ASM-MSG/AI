# PRD Writer

기능 아이디어/티켓을 `docs/prd/` 아래 PRD 문서로 만드는 스킬. 실행 모드는 **인라인** —
PRD의 핵심 입력은 대화에 흐르는 아이디어·요구·맥락이라, 그걸 못 보는 서브에이전트로
격리하면 오히려 품질이 떨어진다.

## 문서 3종의 역할 경계

| 문서 | 질문 | 담당 |
|------|------|------|
| PRD (`docs/prd/*.md`) | 무엇을, 왜 만드는가 | **prd-writer (이 스킬)** |
| 스펙 (`docs/MSG-XXX.md`) | 어떻게 구현하는가 | spec-writer |
| 코드 | 구현 | spec-driven-dev |

파이프라인: 아이디어 → **PRD** → (지라 티켓) → 스펙 → 구현.
PRD가 이미 있으면 spec-writer가 그것을 입력으로 쓴다.

**PRD는 필수 게이트다** — `spec-writer`와 `spec-driven-dev` 양쪽이 PRD 부재 시 이 스킬을 먼저
실행한다. 면제 기준은 CLAUDE.md "개발 파이프라인" 절이 단일 정본("이 작업이 제품 요구사항을
새로 만들거나 바꾸는가") — 커밋 타입만으로 면제가 성립하지 않는다. 면제 판단은 호출 측이 하고,
이 스킬은 호출되면 작성한다. 생성하는 PRD 헤더는 항상 `상태: 초안` — **사용자 승인을 받은 쪽이
헤더를 `상태: 검토됨`으로 갱신해 승인을 파일에 영속화**한다. 게이트 경유면 그 게이트가,
**단독 호출("PRD 만들어줘")이면 이 스킬이 직접** — 요약 보고 후 사용자가 그 자리에서 승인하면
헤더를 즉시 갱신한다(미승인 채 끝나면 `초안`으로 남는 게 맞다 — 다음 게이트가 승인부터 받는다).
초안 상태 PRD는 세션이 바뀌어도 미승인이다.

## 실행 절차

### 1. 입력 확보

- 대화에 아이디어/요구가 있으면 그대로 사용.
- MSG-XX 티켓 번호가 주어졌으면 Jira MCP(`getJiraIssue`)로 조회해 보강.
- 어느 쪽도 없으면 사용자에게 되묻는다 — 추측으로 요구사항을 지어내지 않는다.

### 2. 리서치 (작성 전 필수)

PRD의 "변경 파일 목록"과 다이어그램은 추측이 아니라 실제 코드·실측 확인으로 쓴다:

- **SRS 대조는 PRD에서 항상 해당한다** (BE 레포 2026-08-10 신설, 2026-08-22 이식). 요구사항의
  전역 정본은 BE 레포의 `../FillMap/docs/srs.md` 하나다 — AI 기능 요구사항도 거기 등재돼 있다
  (FR-MEDIA-*, FR-ROUTE-*). 이 기능에 걸리는 영역 절을 먼저 읽는다. 셋 중 하나가 나온다:
  ⓐ 이미 등재된 요구를 상세화하는 PRD면 그 ID를 기능 요구사항 표에 참조로 달고, ⓑ 등재된
  요구와 어긋나면 어느 쪽이 최신 확정인지 확인해 SRS부터 정리하고, ⓒ 신규 요구면 PRD 작성 후
  등재해 ID를 받는다. 단 SRS 파일과 `srs-writer` 스킬은 BE 레포에 있다 — ⓑ·ⓒ의 등재·갱신은
  이 레포에서 직접 하지 않고, 필요한 내용을 사용자에게 알려 BE 레포 세션에서 처리하게 한다.
  등재를 PRD 착수의 차단 조건으로 두지는 않는다 — 게이트가 둘이면 우회 유인만 커지고, 요구사항
  신설은 어차피 이 스킬을 거친다. 다만 PRD를 쓰고 SRS를 안 고치면 다음 PRD가 낡은 요구를
  참조하므로 등재 요청은 미루지 않는다.
- CLAUDE.md "현재 상태 · 다음 작업" 절 — 완료된 티켓과 남은 작업.
- CLAUDE.md "알아둘 함정" 절 — 이미 실측으로 기각된 방향을 요구사항으로 되살리지 않는다
  (프레임 스킵·OpenVINO·macOS 성능 측정).
- 영향받는 코드를 `Grep`/`Read`로 확인 — 존재하지 않는 함수·엔드포인트를 변경 대상에 적지 않는다.
  이 레포는 파일 수가 적다(`server.py`·`bench.py`·`scripts/`) — 실제로 열어본다.
- 성능·정확도 관련이면 `results/MSG-XXX-report.md`의 기존 실측치를 근거로 인용한다.
- BE와의 계약(엔드포인트·응답 필드)에 닿으면 README "API (BE ↔ AI 계약)" 절과 대조한다 —
  BE가 소비 중인 필드를 바꾸는 요구사항이면 PRD에 그 영향을 명시한다.

### 3. 작성

`assets/prd-template.md`를 읽고 그 구조 그대로 작성한다. 파일 경로:

- 티켓 있음 → `docs/prd/MSG-{번호}-prd.md`
- 티켓 없음(아이디어 단계) → `docs/prd/{kebab-slug}.md`, 이후 티켓이 생기면 리네임

작성 원칙:

- **요구사항에는 구현 결정을 넣지 않는다.** "프레임 스트라이드 2로 추론한다"(구현)가 아니라
  "번호판 커버리지 95% 이상을 유지하면서 건당 2분 이내"(비기능 요구). 구현 결정은 스펙 몫.
- 기능 요구사항은 검증 가능한 문장으로 — 각 항목이 나중에 `--smoke` 체크나 실측 리포트의
  판정 기준 하나로 떨어질 수 있게.
- 비기능 요구사항은 성능·프라이버시·계약 호환·운영 중 이 기능에 실제로 해당하는 것만.
  억지로 채우지 않는다.
- 다이어그램은 mermaid(`sequenceDiagram`/`classDiagram`). 필요한 만큼만 — 단순한 변경이면
  시퀀스 하나로 충분하다.
- 확정 못 한 것은 지어내지 말고 "미해결 질문" 섹션에 남긴다.

### 4. 후속 처리

1. 생성한 PRD 경로 + 미해결 질문을 사용자에게 요약 보고. **단독 호출이면 이어서 승인을 묻는다** —
   사용자가 승인하면(미해결 질문은 답을 반영한 뒤) 헤더를 `상태: 검토됨`으로 갱신해 영속화하고,
   승인 없이 끝나면 `초안`으로 남긴다(다음 게이트가 승인부터 받는다). 게이트 경유 호출이면
   이 단계는 호출 측 게이트 몫이라 생략한다.
2. 티켓이 없는 PRD였다면: 지라 티켓 생성(필요 시 분해)을 제안한다 — 티켓 설명은 PRD 요약 +
   PRD 링크로, 사람용 요약 상단 + 🤖 AI 컨텍스트 하단 형식.
3. 사용자가 "스펙 만들어줘/개발 시작해줘"로 이어가면 spec-writer / spec-driven-dev로 넘긴다 —
   이 스킬이 구현 설계까지 내려가지 않는다.

## 테스트 시나리오

- **정상 흐름(아이디어)**: "감지 건수 응답 추가 PRD 뽑아줘" + 대화에 요구 설명 →
  리서치(README API 절, `server.py` 잡 응답) → `docs/prd/detection-count-response.md` 생성 → 티켓화 제안.
- **정상 흐름(티켓)**: "MSG-140 PRD 만들어줘" → Jira 조회 → `docs/prd/MSG-140-prd.md` 생성.
- **에러 흐름**: "PRD 하나 만들어줘"만 있고 대상 기능 불명 + Jira 단서 없음 →
  무엇에 대한 PRD인지 되묻고 진행하지 않음.
